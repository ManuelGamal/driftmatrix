## 1. The question

Serving stacks avoid recomputation by saving model state and restoring it for a
later request that shares a prompt prefix. Agent traffic depends on this more
than any other workload: every turn resends an identical system prompt,
identical tool schemas and a growing history. Production agent traces show
94–96% of prompt tokens served from cache (TraceLab, arXiv 2606.30560).

Restoring is assumed to be invisible. This project measures whether it is.

### 1.1 The claim under test

> Serving an identical request from restored state instead of recomputing it
> changes the model's output distribution unless the reuse boundary is aligned
> with the engine's physical micro-batch; the size of that change depends
> strongly on architecture; and aligning the boundary removes it.

The behavioural question stays central: **does the change alter which tool the
agent calls?** A shifted logprob is a curiosity. A changed tool call is a
behavioural change caused by an optimization meant to be invisible.

### 1.2 The mechanism

Restoring a saved state returns bit-identical bytes, so the restore itself
cannot introduce a difference. The difference comes from **how the two arms
segment the prompt.**

llama.cpp evaluates a prompt in physical micro-batches of `n_ubatch` tokens
(default 512). With the prompt split `[prefix | suffix]` at reuse boundary `k`:

- **Recompute** tiles the whole prompt from position 0: `[0, U) [U, 2U) …`
- **Restore** tiled the prefix from 0 when it was first evaluated, and tiles the
  suffix afresh from `k`: `[0, U) … [·, k)` then `[k, k+U) …`

The two tilings coincide **exactly when `k` is a multiple of `n_ubatch`**.
Otherwise every operation that reduces over a micro-batch — matrix
multiplication, attention, the chunked linear-attention scan — may accumulate
floating-point error in a different order. Addition is not associative, so the
results can differ.

Why the magnitude should depend on architecture:

| | Dense / full attention | Sliding window | `linear_attention` (recurrent) |
|---|---|---|---|
| What persists between tokens | per-token K/V | per-token K/V, bounded window | one fixed-size state matrix |
| Is a persisted value a cross-token reduction? | No — `K_i = W_k x_i` | No | **Yes** — `S_i = f(S_{i−1}, k_i, v_i)` |
| Where a tiling difference goes | a slightly different attention output for that step; nothing persists | same | **into the state**, carried forward and re-transformed at every later token |

**Predictions, each falsifiable:**

1. **Exactness:** restore is bit-exact iff `k mod n_ubatch = 0`, on every
   architecture. Changing `n_ubatch` must move the set of exact reuse
   boundaries with it (gate G1).
2. **Magnitude:** at misaligned boundaries, divergence is small on dense and
   sliding-window models and large on the hybrid.
3. **Compounding:** on the hybrid only, divergence grows across decoded tokens.
4. **Mitigation:** snapping each reuse boundary down to a multiple of `n_ubatch`
   restores exactness in agent traffic.

### 1.3 What G0 and G1 established

Full record: `docs/findings/2026-09-10-g0.md`, raw reports in
`docs/findings/g0/`, every number regenerated by `scripts/g0_analyze.py`.

On llama.cpp `b10839-0cae43063`, one synthetic prompt per model, `-ub 512`:

| Model | Restore at a multiple of 512 | Restore elsewhere: max TV / max JSD |
|---|---|---|
| Qwen3-4B, dense | bit-exact | 0.0001 / < 0.0001 |
| Spark-X2.5-4B, sliding window | bit-exact at 512; not at 1024 (TV 0.0028) | 0.0017 / 0.0001 |
| Ornith-1.5-9B, hybrid | **bit-exact** | **0.76 / 0.46** |

On the hybrid, JSD rose from 0.0011 to 0.29 (k=640) and from 0.0001 to 0.46
(k=672) across a single decoded token. Every validity check passed: identical
recompute floors, restore arms that evaluated exactly their suffix, recompute
arms that evaluated the whole prompt, saved slots holding exactly `k` tokens.

**What G0 did not establish:** a tool-call change (the prompt lacked a chat
template, so the model never entered tool-calling mode), statistical
significance (one prompt per model), a controlled architecture comparison
(quantization differed: IQ4_XS vs Q4_K_M), or that tiling is the only
mechanism. Spark at k=1024 is an open anomaly; its sliding window is also 512.

**G1** (`docs/findings/2026-09-10-g1.md`) varied `n_ubatch` over 256, 512 and
1024 on Ornith-1.5-9B and Qwen3-4B, both Q4_K_M, with 11 reuse boundaries per
run. **All 66 restores were exact at multiples of `n_ubatch` and inexact
elsewhere — zero contradictions.** The exact set moved with `n_ubatch` as
predicted (k=512 exact at 256 and 512, not 1024; k=768 exact at 256 only).
Prediction 1 holds.

Magnitude over 16 positions, misaligned boundaries, one ~1,900-token prompt per
model: hybrid median worst-position TV 0.2374 (range 0.0808–0.5734), greedy
token changed in 5 of 23 cases; dense median 0.0092 (0.0025–0.0233), 0 of 23.
About 26× by median. **These supersede G0's magnitudes**, which compared 8
positions on a shorter prompt and understated the dense model's drift: it is
small, not negligible. Boundaries within a run share one prompt, so these are
descriptive, not population estimates.

| Source | What it supports | Confidence |
|---|---|---|

| **SGLang #21846** | Hybrid cache compatibility "remains limited"; agentic hybrid scheduling in progress | Corroboration |
| **vLLM RFC #54506** | Shape-dependent kernel arithmetic makes verify and decode non-bit-identical on a hybrid | Analogous mechanism |

### 1.5 Prior art — what this project must not claim

- **That prompt caching can change output.** llama.cpp documents it.
- **Batch invariance in general.** Thinking Machines Lab, "Defeating
  Nondeterminism in LLM Inference" (Sept 2025); shipped in vLLM as
  `VLLM_BATCH_INVARIANT`.
- **Agent-workload characterization on dense models.** TraceLab (arXiv
  2606.30560), vLLM × Mooncake, Policy-Driven Runtime Layer (arXiv 2605.27744).
- **Cache-aware prompt ordering.** LangChain, "Deep Agents Prompt Caching".

What remains, as far as the searches found: **the exact condition** under which
reuse is lossless in llama.cpp, **how the magnitude depends on architecture**,
**the behavioural consequence in agent traffic**, and **a measured mitigation**.

## 2. Scope

### 2.1 In scope

- Engine: **llama.cpp `llama-server`**, pinned build stamped into every row,
  driven through its slot save/restore API with both arms proven by the
  server's own `timings.prompt_n`.
- A three-level architecture ladder, **quantization-matched at Q4_K_M** (§3.1).
- The mechanism test: `n_ubatch` ∈ {256, 512, 1024} (gate G1).
- The main study: restore vs recompute at natural and snapped reuse boundaries,
  in chat-templated agent traffic that produces real tool calls.
- A `pip`-installable harness plus a written study.

### 2.2 Out of scope

- **Speed, hit rate, TTFT, throughput as results.** Instrumentation only.
- **Batch invariance in general**, and **kernel fixes** inside llama.cpp.
- **Claims about vLLM or SGLang.** Their evidence motivates; this study measures llama.cpp.
- **Per-layer state attribution.** `llama-server` slot files are opaque dumps;
  state comparison is byte-level only (§5.3). Per-layer attribution would need
  the bindings path and is deferred.
- **Multimodal turns, long-context reasoning, state quantization.** Deferred.

### 2.3 The role of the agent framework

LangGraph generates the traffic: stable system prompt, stable tool schemas,
growing history, deterministic mock tools, real tool-call round trips. It is the
traffic generator, not the contribution.

### 3.1 The architecture ladder, quantization-matched

| Level | Model | Quant | Architecture | Role |
|---|---|---|---|---|
| 3 | Ornith-1.5-9B | **Q4_K_M** | `qwen35`: 3× `linear_attention` + 1× full, recurrent state | Treatment |
| 2 | Spark-X2.5-4B | **Q4_K_M** | `spark2_5`: 3× sliding window (512) + 1× full | Structural control |
| 1 | Qwen3-4B | **Q4_K_M** | `qwen3`: dense | Baseline |

G0 compared an IQ4_XS hybrid against Q4_K_M controls. Quantization selects
kernels, so the main study matches it. The Ornith IQ4_XS run is kept as a
secondary replication, not as the comparison.

Both Ornith GGUFs carry an MTP block; it is inactive unless `--spec-type` is
passed, and it never is.

### 3.2 Server configuration — identical for every run

```
-c 8192 -ngl 99 -np 1 -b 2048 -ub <U> --cache-ram 0 --ctx-checkpoints 0 --slot-save-path <dir>
```

plus `--swa-full` for Spark and `--jinja` wherever chat templates are rendered
by the server. `U` is 512 except in gate G1. Each flag exists to remove a
confound: no speculative decoding, f16 KV cache, one slot, no host-RAM prompt
cache that could feed a recompute arm, no automatic checkpoints.

### 3.3 Hardware

RTX 4060 Laptop, 8 GB; llama.cpp `b10839` Windows CUDA build. Largest footprint
is Ornith Q4_K_M (~5.5 GB) plus compute buffers, which fits at `-c 8192`; at
`-ub 1024` the context drops to 4096 if needed.

## 4. Experiment design

### 4.1 Gate G1 — the mechanism test

Before the main study, prediction 1 must survive. For each `n_ubatch` ∈ {256,
512, 1024}, one prompt of ~2000 tokens, reuse boundaries
`k` ∈ {256, 384, …, 1536}:

- **exact** means both arms produce identical tokens *and* identical top-k
  logprobs at every position;
- the prediction is **exact iff `k mod n_ubatch = 0`**.

The discriminating boundaries: `k = 512` is predicted exact at 256 and 512 but
not at 1024; `k = 768` exact at 256 only. If the exact set does not move with
`n_ubatch`, tiling is falsified and §1.2 is rewritten before any further work.

Run on Ornith Q4_K_M (large effect) and Qwen3-4B (small effect). Spark is added
to isolate the k=1024 anomaly by varying `n_ubatch` independently of its window.

### 4.2 Main-study factors

| ID | Factor | Levels |
|---|---|---|
| **T** | Arm (treatment) | restore · recompute |
| **B** | Reuse boundary | **natural** (end of the previous turn, wherever it falls) · **snapped** (natural boundary rounded down to a multiple of `n_ubatch`) |
| **P** | Prefix length | short (~1K tokens) · long (~6K tokens) |
| **S** | Request stratum | **explicit** (one tool and its arguments are unambiguous) · **ambiguous** (more than one plausible tool, or an under-specified argument) |
| **A** | Architecture (blocking) | levels 3, 2, 1 |

2 × 2 × 2 = 8 conditions per architecture, each with both arms, each
replicated twice. **B** carries the mitigation: a snapped boundary re-evaluates
`b mod n_ubatch` extra prompt tokens (≤ `n_ubatch − 1`) and should make restore
exact. Every natural boundary also records `k mod n_ubatch`, so the analysis
can split natural boundaries by their actual alignment.

**Why S replaced the continuation factor.** Continuation length stopped making
sense once traces became tool calls: G2's completions were bare tool calls of
81–151 characters that end the turn, so a 32-token continuation truncates many
of them and a 256-token one is never reached. Generation now runs to the end of
the turn, capped at 192 tokens, and compounding is measured across positions
within the output. The freed factor carries the stratum: G2 found explicit
requests produce near-certain decisions (90 of 90 exact), and G1 showed restore
flips a decision only near a tie, so an explicit-only study risks a behavioural
null caused by trace design rather than by the mechanism.

### 4.3 Forcing and proving the arms

Through `llama-server`:

- **Restore:** erase slot → evaluate `prompt[:k]` → save → erase → restore →
  complete the full prompt with caching on.
- **Recompute:** erase slot → complete the full prompt with caching off.

Both are **proven**, not assumed: a restore arm is valid only if its
`timings.prompt_n` equals the suffix length (the server can silently reprocess,
llama.cpp #20225), and a recompute arm only if it evaluated the whole prompt
(a host-side cache could hand it state it never computed). Each saved slot must
hold exactly `k` tokens.

### 4.4 Agent-shaped traces

Generated with LangGraph and **rendered through each model's own chat template
with its tool-call format**, so the model is in tool-calling mode:

| Property | Construction |
|---|---|
| System prompt, tool schemas | Identical across turns and sessions |
| History | Monotonic accumulation of rendered user, assistant and tool messages |
| Tool round trips | Deterministic mock tools, pure functions of their arguments |
| Natural boundary | Token length of the rendered conversation before the current turn |
| Prefix length | Padded history to satisfy **P** |

**Strata.** An ambiguous conversation is its explicit twin with only the final
user request replaced, so both strata share the same history and the stratum
contrast is paired. Explicit requests name one tool and its arguments ("Look up
record 153"). Ambiguous requests stay answerable with a tool call but leave a
real choice: more than one plausible tool ("Give me something on record 42"),
or an argument to infer from history ("Add up the numbers from earlier"). They
have no single correct call, so correctness is not scored for them; the
recompute arm's own call is the reference. The stratum must earn its place: G2
requires ambiguous requests to keep at least 90% tool calls **and** to show a
lower median decision margin than explicit ones.

**Rendering.** `llama-server`'s `/apply-template` accepts `messages` only, not
`tools`, so prompts are rendered offline from the chat template embedded in each
GGUF (`tokenizer.chat_template`) with jinja2, configured the way HuggingFace
renders chat templates: `trim_blocks` and `lstrip_blocks` on, loop controls
enabled, `raise_exception` provided, and a `tojson` filter that does **not**
HTML-escape. (jinja2's built-in `tojson` escapes `<`, `>` and `&`, which would
silently change the rendered tool schemas.) Thinking is disabled
(`enable_thinking = false`) so the generation budget reaches the tool call.
Before use, the renderer must reproduce `/apply-template` byte for byte on
tool-less conversations for every model.

**Tool-call formats differ by model**, taken verbatim from each template, and
each gets its own parser:

| Model | Emitted tool call |
|---|---|
| Ornith (Qwen3.5 template) | `<tool_call>
<function=NAME>
<parameter=ARG>
VALUE
</parameter>
</function>
</tool_call>` |
| Qwen3-4B | `<tool_call>
{"name": "NAME", "arguments": {…}}
</tool_call>` |
| Spark-X2.5-4B | `<tool_call>NAME<arg_key>ARG</arg_key><arg_value>VALUE</arg_value></tool_call>` |

Argument values are canonicalised — JSON-decoded where they parse, keys sorted —
before hashing, so an identical call always hashes identically.

360 turns per model — 90 in each prefix-length × stratum cell — frozen and content-hashed.

### 4.5 Two measurement modes

**Free-running (headline):** both arms generate at temperature 0 until the end
of the turn, capped at 192 tokens; record exact-match, first-divergence position,
**parsed tool call**, final answer.

**Teacher-forced (instrument):** each arm scores the other's output, giving
per-position distribution differences under identical context.

## 5. Metrics

### 5.1 Behavioural (primary)

- **Tool-call agreement** — same tool name and same canonicalised arguments.
- **Exact-match rate** of the completion.
- **First-divergence position**, right-censored when the two outputs are identical.
- **Final-answer agreement** on the verifiable subset.
- **Decision margin (covariate).** On the recompute arm only: the smallest gap
  between the top-1 and top-2 logprobs at any generated position through the end
  of the first complete tool call. Pre-registered bins: **near-tie** below 0.5
  nats, **contested** 0.5 to 2 nats, **confident** 2 nats or more. Taken from the
  recompute arm so that stratifying by it never selects on the treatment's
  outcome. (G0's hybrid flipped a token whose recompute-arm margin was 1.13 nats.)

### 5.2 Distributional (supporting)

**Jensen–Shannon divergence and total variation** over each arm's top-k
logprobs, with both re-expressed over the union of their supports plus one
`<other>` bucket for the missing mass. Computed at positions whose context is
still identical in both arms (0 through first divergence).

**Never compare arms by the maximum logprob difference across the top-k.** It is
dominated by low-probability tail tokens; in G0 it made negligible drift on the
dense and sliding-window models read as 0.35–1.79 nats.

**Exactness** is separate and binary: identical tokens and bitwise-identical
top-k logprobs at every position.

### 5.3 State comparison

After both arms finish, each slot is saved; the two files are compared byte for
byte (equal / number of differing bytes). This detects divergent state even when
output tokens agree. It cannot attribute a difference to a layer (§2.2).

### 5.4 Figures

1. **Exact-set grid** (G1): reuse boundary × `n_ubatch`, exact or not.
2. **Headline:** tool-call disagreement rate by boundary (natural / snapped)
   across the three levels, with CIs.
3. **Compounding:** JSD by position after the reuse boundary, per level.

## 6. Statistics

### 6.1 Effects against a measured floor

Per turn *p* and condition *c*:
`effect(c, p) = divergence(restore, recompute) − divergence(recompute₁, recompute₂)`.
The bootstrap runs on the difference. A condition is **self-inconsistent** when
its median per-turn mean JSD exceeds 2× the recompute arm's self-comparison
median — a pre-specified engineering threshold.

G0 found the recompute floor bit-exact on all three models. If that holds in the
main study, any nonzero divergence is unambiguous.

### 6.2 Tests

Paired bootstrap over turns (10,000 resamples); Holm–Bonferroni within three
declared families, never pooled; confidence intervals on every effect including
nulls.

| Family | Members | Size |
|---|---|---|
| A — behavioural divergence | 8 conditions × 3 architectures | 24 |
| B — distributional effects | 8 conditions × 2 statistics (mean, max JSD), level 3 | 16 |
| C — mechanism contrasts | snapping effect; snapping × architecture; hybrid vs dense magnitude at natural boundaries; P compounding; stratum effect (ambiguous vs explicit) | 5 |

### 6.3 The contrasts that carry the contribution

1. **Snapping:** natural boundaries diverge; snapped boundaries do not.
2. **Architecture magnitude:** at natural boundaries, divergence on the hybrid
   exceeds the dense baseline — and the sliding-window control sits with the
   dense one, which is what attributes it to recurrent state rather than to
   interleaved layer structure.
3. **Compounding:** on the hybrid, divergence grows with prefix length and
   across positions within the output.
4. **Stratum and margin:** tool-call changes concentrate in the ambiguous stratum
   and in the near-tie and contested margin bins. The margin analysis is a
   pre-registered secondary analysis reported with CIs, outside the Holm families.

Interaction claims are stated relative to an additive null on the JSD scale.

### 6.4 Pre-registration

Analysis plan, family membership and thresholds committed and tagged **after G1
and after the floor is measured, before any main-study treatment effect is
examined.** It fixes the ambiguous request templates, the margin definition
and the margin bins.

### 6.5 Power, and designing for a null

Detect a per-turn divergence rate of **2% at 80% power, α = 0.05** against a
zero floor: 80 turns required; 360 planned gives 99.9% overall and
84% within each of the four prefix-length × stratum cells of 90 turns. Achieved power is
reported with the result.

A null is pre-committed as publishable: *at natural agent-turn boundaries on
llama.cpp build X, restore changed no tool calls in N turns, bounding the rate
below Y% (95% CI).*

The `Engine` protocol, `FakeEngine`, the llama-cpp-python adapter and the

They are not on the measurement path.

### 7.2 Data

Per `(model, condition, replicate, arm, mode, session, turn, position)`:
factor levels, `k`, `k mod n_ubatch`, `n_ubatch`, top-k ids and logprobs,
chosen token, parsed tool name and argument hash, `prompt_n`, arm-validity
flags, outcome, engine build, quantization, trace hash, run id. Parquet on
local storage, gitignored; findings and sanitized reports committed.

### 7.3 Failure as data

Every run resolves to `ok` · `unsupported` · `crashed` · `timeout` ·
`restore_not_used` · `recompute_not_clean` · `save_mismatch`. Invalid arms are
counted and published, never silently dropped.

## 8. Validity controls

- **Positive control (natural):** misaligned restore on the hybrid, which G0
  showed diverging. If the main-study harness cannot see it, it is broken.
- **Negative control 1:** snapped boundaries must be bit-exact on every model.
- **Negative control 2:** the recompute floor must be bit-exact.
- **Negative control 3:** the dense baseline at natural boundaries must change
  no more tool calls than chance allows, with distribution drift in the range G1
  measured (worst-position TV of order 0.01).
- **Arm proofs** on every run (§4.3); **pinned build**; **deterministic tools**;
  **pre-registration** (§6.4).

## 9. Testing the harness

Every analysis layer is a pure function under unit test: metrics against
distributions with known answers; the bootstrap and Holm correction against a
coverage simulation and a reference implementation; `g0`/`g1` against a scripted
fake server that models micro-batch tiling, silent reprocessing and host-cache
leakage; GGUF reading against a synthetic file; the gate against golden files.

> reuse boundary is a multiple of `n_ubatch`. At natural agent-turn boundaries,
> restore changed the tool call in *W*% of ambiguous-request turns (explicit: *W′*%) on a hybrid recurrent model
> (95% CI [*a*, *b*]) versus *~0*% on quantization-matched dense and
> sliding-window models; snapping boundaries to micro-batch multiples, at a cost
> of at most `n_ubatch − 1` re-evaluated tokens, reduced it to *~0*%.

**Success criteria:** G1 decided either way and reported; all arms proven;
controls behave or their failure is diagnosed; every effect carries a CI; claims
scoped to build and quantization; prior art cited up front. A high divergence
rate is an outcome, not a criterion.
