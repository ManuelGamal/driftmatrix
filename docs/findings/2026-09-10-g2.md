# G2 findings — chat-template rendering and tool calls

Date: 2026-09-10
Engine: llama.cpp `llama-server` build `b10839-0cae43063`, Windows, CUDA, RTX 4060 Laptop (8 GB)
Raw reports: [`g2/`](g2/) (no local paths)

**Verdict: the rendering and tool-call checks of gate G2 passed on all three
models.** The gate's remaining item is pre-registration, which waits on one
design decision recorded at the end of this note.

## Why this gate exists

G0 and G1 used raw text prompts, so no model was ever in tool-calling mode and
"did restore change the tool call" could not be measured. The main study needs
prompts rendered through each model's chat template with tool definitions — and
the server's own renderer, `/apply-template`, accepts no `tools`. Prompts are
therefore rendered offline. G2 establishes that offline rendering is exactly the
server's, and that the rendered prompts actually produce tool calls.

## Server configuration

```
--jinja -c 8192 -ngl 99 -np 1 -b 2048 -ub 512 --cache-ram 0 --ctx-checkpoints 0 --slot-save-path <dir>
```

plus `--swa-full` for Spark. All three models Q4_K_M.

## Check 1 — offline rendering is byte-exact (tool-less)

`scripts/g2_render_check.py`: 12 tool-less conversations of increasing length
per model, offline render compared with `/apply-template` under every
combination of `add_generation_prompt` and `enable_thinking`.

| Model | add_generation_prompt=True, thinking True | thinking undefined | thinking False | add_generation_prompt=False |
|---|---|---|---|---|
| Ornith-1.5-9B | **12/12** | **12/12** | 0/12 | 0/12 |
| Qwen3-4B | **12/12** | **12/12** | 0/12 | 0/12 |
| Spark-X2.5-4B | **12/12** | **12/12** | 0/12 | 0/12 |

The zeros are expected: the server renders with a generation prompt and thinking
on. "True" and "undefined" are equivalent in all three templates — for Ornith and
Qwen3 by their branch structure, for Spark because line 5 of its template is
`{%- set enable_thinking = enable_thinking | default(true) %}`.

## Check 2 — prompts with tools match the server, and produce tool calls

`scripts/g2_toolcalls.py`: 30 conversations per model, each with 3 completed
tool round trips and a final request, tools on, thinking off, greedy, up to 192
new tokens. Each conversation runs twice: rendered offline and completed through
`/completion` (the study's path), and sent to `/v1/chat/completions`, where the
server renders it and parses tool calls itself.

| Model | Tool-call format | Prompt tokens | Prompt tokens match server | Parser agrees with llama.cpp | Tool-call rate | Expected tool | Exact expected call |
|---|---|---|---|---|---|---|---|
| Ornith-1.5-9B | `qwen_xml` | 725–770 | 30/30 | 30/30 | 30/30 | 30/30 | 30/30 |
| Qwen3-4B | `qwen_json` | 557–594 | 30/30 | 30/30 | 30/30 | 30/30 | 30/30 |
| Spark-X2.5-4B | `spark_argkv` | 428–467 | 30/30 | 30/30 | 30/30 | 30/30 | 30/30 |

Checked for triviality: token counts match conversation by conversation and no
server count was missing; there were no chat errors; neither parser returned
"no call" on any conversation, so agreement is between 90 real tool calls. Every
output was a bare tool call with no text before `<tool_call>` (81–151 chars).

## What this shows

1. **The study's prompts are the server's prompts.** Byte-exact on tool-less
   conversations, and token-count-identical on every conversation carrying tools
   — including the server's conversion of JSON-string tool arguments into the
   objects some templates require.
2. **The three incompatible tool-call formats are parsed correctly**, agreeing
   with llama.cpp's own parser on every call.
3. **Chat-templated prompts put all three models in tool-calling mode**, well
   above the 90% gate.

## Traps found and handled on the way

- `/apply-template` accepts `messages` only, not `tools`.
- jinja2's default `tojson` HTML-escapes `<`, `>`, `&` **and sorts keys**
  (policy `json.dumps_kwargs = {"sort_keys": True}`, verified on 3.1.6). Either
  would silently rewrite every tool schema; the renderer overrides both, pinned
  by tests.
- The three models emit three incompatible tool-call formats; each has its own
  parser, validated against the template's own serialisation of a tool call.
- Spark's template silently defaults `enable_thinking` to true.

## Limits

- **Token-count equality is not byte equality.** A same-length substitution in a
  prompt carrying tools would pass. It is backed by the byte-exact tool-less
  check, round-trip parsing of each template's own tool-call serialisation, and
  unit tests of the `tojson` override.
- **Explicit requests only.** See below.

## Open decision before pre-registration

Every one of the 90 requests produced exactly the expected call. The requests
are explicit ("Look up record 153"), so the models' tool decisions are close to
certain. G1 showed restore-induced drift changes a greedy token only when a
decision is near a tie (5 of 23 misaligned hybrid restores, on a low-confidence
prompt). With traces this unambiguous, the main study's behavioural headline —
restore changed the tool call — risks a null result caused by the traces rather
than by the mechanism. Real agent traffic contains genuinely ambiguous decision
points. How the traces should represent them has to be settled before the
analysis plan is frozen.

## Strata check (spec v4.2) and what it changed

Both strata were run on all three models: the same 30 conversations, explicit
final requests versus ambiguous ones, with top-10 logprobs for the decision
margin. Reports: `g2/g2_toolcalls_<model>_<stratum>.json`. Breakdown regenerated
by `python scripts/g2_types.py --dir docs/findings/g2`.

**Determinism across server restarts.** The explicit rerun reproduced the first
explicit run byte for byte: 30/30 identical outputs and 30/30 identical parsed
calls on every model.

### Result against the v4.2 gate

| Model | Explicit calls | Explicit median margin | Ambiguous calls | Ambiguous median margin | v4.2 verdict |
|---|---|---|---|---|---|
| Ornith | 30/30 | 6.92 | 26/30 | 5.74 | below 90% call gate |
| Qwen3 | 30/30 | 9.76 | 20/30 | 9.19 | below 90% call gate |
| Spark | 30/30 | 7.77 | 25/30 | 3.67 | one parser disagreement; below gate |

Margins here are the v4.2 definition, measured over tool calls only.

### Broken down by request type

Calls, and median margin among calls (nats):

| Request type | Kind | Ornith | Qwen3 | Spark |
|---|---|---|---|---|
| "Give me something on record N" | tool choice | 6/6, 7.88 | 6/6, 9.98 | 6/6, 9.25 |
| "Can you total up records A and B?" | tool choice | 6/6, 7.82 | 6/6, 7.47 | 6/6, 4.04 |
| "Pull up that record again" | under-specified | 4/6, 4.28 | 5/6, 9.17 | 6/6, 3.94 |
| "Add up the numbers from earlier" | under-specified | 6/6, 1.37 | 2/6, 0.69 | 5/6, 2.30 |
| "Write that up for me" | under-specified | 4/6, 0.89 | 1/6, 0.04 | 2/6, 0.09 |
| **All tool choice** | | **12/12, 7.82** | **12/12, 9.57** | **12/12, 6.95** |
| **All under-specified** | | **14/18, 1.93** | **8/18, 3.35** | **13/18, 2.30** |

- **Tool-choice ambiguity never produced a near-tie.** Every request got a tool
  call, and decisions were about as confident as explicit ones.
- **Under-specified requests were the only source of near-ties** — and the same
  requests sometimes ended without a call: a clarifying question ("I'm not sure
  what you'd like me to write up"), or the tool's output written as text
  ("# Batch 91 / status nominal").

A stratum vague enough to create near-ties is vague enough that a model sometimes
declines to act. Dropping the under-specified requests would have removed every
near-tie; holding them to a 90% call gate would reject the stratum.

### Decision (spec v4.3)

The behavioural outcome is the agent's **action**: a tool call with its
arguments, or no call. A restore that turns a tool call into a clarifying
question is a behavioural change. The margin became an **action margin**,
defined for every turn: the smallest top-two gap over the first generated
position (act or not) and the positions of the tool call (which tool, which
arguments). Explicit requests keep the 90% call gate, which validates the
tool-call pipeline; the ambiguous stratum is held to a 50% call floor plus the
margin check. The ambiguous stratum is re-run under this definition.

### Parser disagreement — unresolved

One Spark ambiguous call, `format_report` with a body and a title, parsed to the
same tool name but different argument hashes in our parser and llama.cpp's. Our
parse reproduces the template's own serialisation rule. Fourteen hypotheses for
llama.cpp's reading (dropped arguments, truncation, quoting, key/value splitting,
type coercion, swapped keys) reproduce none of its hash. Reports now store both
parsers' full arguments, so the re-run identifies it directly.
