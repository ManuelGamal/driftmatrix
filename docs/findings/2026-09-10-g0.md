# G0 findings — state save/restore on llama.cpp

Date: 2026-09-10
Engine: llama.cpp `llama-server` build `b10839-0cae43063`, Windows, CUDA, RTX 4060 Laptop (8 GB)
Raw reports: [`g0/`](g0/) (local paths stripped). Every number below is regenerated by
`python scripts/g0_analyze.py`.

## Setup

Server flags, identical for every model:

```
-c 8192 -ngl 99 -np 1 -b 2048 -ub 512 --cache-ram 0 --ctx-checkpoints 0 --slot-save-path <dir>
```

No `--spec-type` (the MTP head was never used), no KV-cache quantization (f16),
no host-RAM prompt cache, no context checkpoints. Spark additionally ran with
`--swa-full`, without which a sliding-window cache discards entries a restore
past the window would need.

| Level | Model | Quant | Architecture | Prompt tokens |
|---|---|---|---|---|
| 3 | Ornith-1.5-9B (MTP GGUF, MTP unused) | IQ4_XS | `qwen35`: 3× linear attention + 1× full, recurrent state | 1390 |
| 2 | Spark-X2.5-4B | Q4_K_M | `spark2_5`: 3× sliding window (512) + 1× full | 1466 |
| 1 | Qwen3-4B | Q4_K_M | `qwen3`: dense, full attention | 1291 |

Prompt: one synthetic 30-turn agent session from `traces.generator`, sent as raw
token ids. Greedy decoding (`temperature 0`, `top_k 1`), 32 new tokens, top-10
logprobs per position.

Each split `k`: erase slot → evaluate `prompt[:k]` → save → erase → restore →
complete the full prompt (restore arm). Compared against: erase → complete the
full prompt with prompt caching off (recompute arm).

## Validity — all checks passed for all three models

- **Floor:** recompute vs recompute bit-identical, top-1 logprob gap exactly 0.
- **Restore really used:** every restore arm's `timings.prompt_n` equalled its suffix length exactly.
- **Recompute really clean:** every recompute arm evaluated the whole prompt.
- **Saved slot exact:** `n_saved` equalled `k` at every split.

## Result

arm's top-10 plus an `<other>` bucket, at every position whose context is still
identical in both arms (0 through the first divergence).

Ornith's JSD by position at the misaligned splits: **0.0011 → 0.2923** (k=640) and

Ornith's decoded output (first 12 tokens):

- recompute, and restore at 512 and 1024: `' [ conversation has been cut off here.\n\n<think>\nThe'`
- restore at 640: `' [context] 91\n\nUser [New Session]:'`
- restore at 672: `' [ few-shot examples above. Follow the same pattern.\n\n'`

## What this shows

**1. The reuse boundary's alignment with the physical micro-batch governs
exactness.** llama.cpp evaluates a prompt in micro-batches of `n_ubatch`. A
restore at a multiple of 512 tiles the remaining prompt exactly as recompute
does, and was bit-exact for the hybrid and the dense model. A restore anywhere
else tiles it differently and was not bit-exact for any model.

**2. The size of the effect depends strongly on architecture.** Under identical
misaligned splits, the dense model moved at most 0.0001 of its probability mass
and the sliding-window model at most 0.0028. The hybrid moved up to 0.76.

**3. On the hybrid, the discrepancy grew by two to three orders of magnitude
across one decoded token.** That is what the design predicts for a difference
that enters a recurrent state and is carried forward — and neither control
showed any comparable growth.

## What this does not show

- **Not a tool-call change.** The prompt is raw `User:/Assistant:` text with no
  chat template, so Ornith treated it as a document and never entered
  tool-calling mode. The outputs differ in meaning, but tool-call agreement was
  not measured. The trace generator must apply each model's chat template and
  tool-call format before this outcome can be tested.
- **Not statistically established.** One prompt per model. The architecture
  contrast is a strong day-one signal, not a result.
- **Not a controlled architecture comparison yet.** The three models differ in
  quantization (IQ4_XS vs Q4_K_M), tokenizer, prompt length and size. Quantization
  in particular selects different kernels. Ornith also exists as Q4_K_M locally;
  the comparison should be rerun quant-matched.
- **Tiling is not proven to be the only mechanism.** It is the explanation the
  aligned/misaligned pattern supports, not a proof. The direct test is to vary
  `-ub`: if tiling is the cause, the set of bit-exact splits must move with it.

## Anomaly

Spark at k=1024 — aligned to the micro-batch — was not bit-exact (TV 0.0028)
while k=512 was. The sliding window is also 512, so at Spark "aligned" means
aligned to two things at once. Unexplained; to be isolated by varying `-ub`
independently of the window.

## Two mistakes caught during analysis

Recorded so they are not repeated:

1. **A tail-dominated metric.** An early comparison used the maximum logprob
   difference across the top-10 candidates. Low-probability candidates dominate
   that number, and it made the dense and sliding-window models look as disturbed
   as the hybrid (0.35–1.79 nats). Probability-weighted, their drift is
   negligible. Use JSD/TV; `g0_analyze.py` carries a warning to that effect.
2. **An unverified reading of a token.** Position 1 was first assumed to be a
   tool name. Decoding it from the model's own vocabulary showed it is not.

## Prior art

llama.cpp's server README, on `cache_prompt`:

> "Because (depending on the backend) the logits are **not** guaranteed to be
> bit-for-bit identical for different batch sizes (prompt processing vs. token
> generation) enabling this option can cause nondeterministic results."

So "prompt caching can change output" is documented. Not documented, as far as
this search found: the condition under which reuse is exact (a reuse boundary on
a micro-batch multiple), how the magnitude depends on architecture, and the
behavioural consequence in agent traffic. Those are what remain for this project.

## Consequences for the plan (pending decision)

- **G1** should sweep the micro-batch size (`-ub`), not a GDN kernel chunk size:
  the bit-exact splits must track `n_ubatch` if tiling is the mechanism.
- **Traces** must use the model's chat template and tool-call format.
- **Architecture comparison** must be quantization-matched.
- **Mitigation worth testing:** snapping reuse boundaries to `n_ubatch`
  multiples would make restore exact at no compute cost, if the pattern holds.
