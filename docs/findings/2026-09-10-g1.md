# G1 findings — does the exact set track `n_ubatch`?

Date: 2026-09-10
Engine: llama.cpp `llama-server` build `b10839-0cae43063`, Windows, CUDA, RTX 4060 Laptop (8 GB)
Raw reports: [`g1/`](g1/) (local paths stripped). Every number below is regenerated by

```
python scripts/g1_analyze.py --label ornith_q4km --dir docs/findings/g1
python scripts/g1_analyze.py --label qwen3_dense --dir docs/findings/g1
```

**Verdict: G1 passed.** The set of reuse boundaries at which restore is
bit-exact moved with the micro-batch size exactly as tiling predicts, on both
architectures, with zero contradictions in 66 restores.

## Why this test

G0 found restore exact at reuse boundaries that were multiples of 512 — the
default `n_ubatch` — and inexact elsewhere. One `n_ubatch` cannot distinguish
micro-batch tiling from anything else that repeats every 512 tokens. G1 changes
`n_ubatch` and asks whether the exact set follows it. Tiling makes a prediction
that can fail: `k = 512` exact at 256 and 512 but not at 1024; `k = 768` exact
at 256 only.

## Setup

```
-c 4096 -ngl 99 -np 1 -b 2048 -ub {256, 512, 1024} --cache-ram 0 --ctx-checkpoints 0 --slot-save-path <dir>
```

| Model | Quant | Architecture | Prompt tokens |
|---|---|---|---|
| Ornith-1.5-9B | Q4_K_M | `qwen35`, hybrid, recurrent state | 1911 |
| Qwen3-4B | Q4_K_M | `qwen3`, dense | 1793 |

One synthetic 45-turn agent prompt per model (raw text, no chat template), 11
reuse boundaries `k` ∈ {256, 384, …, 1536}, greedy, 16 new tokens, top-10
logprobs. The recompute reference is computed once per server run.

**Exact** means identical tokens *and* bitwise-identical top-10 logprobs at all
16 positions.

## Validity

All six runs: recompute floor bit-exact; both recompute arms evaluated the whole
prompt; every restore arm evaluated exactly its suffix; every saved slot held
exactly `k` tokens. (The `PREDICTION_HOLDS` verdict is unreachable unless all of
these hold.)

## What this shows

1. **Exactness condition confirmed.** On llama.cpp, restoring saved state is
   bit-exact exactly when the reuse boundary is a multiple of `n_ubatch`, for
   both a dense and a hybrid recurrent model. The prediction was specific enough
   to fail and did not.
2. **Misaligned restore is never exact — on either architecture.** The dense
   model is not immune; its divergence is small, not zero.
3. **The hybrid diverges far more.** Median worst-position TV is about 26× the
   dense model's (0.2374 vs 0.0092), and a greedy token changed in 5 of 23
   misaligned restores against 0 of 23.

## Correction to G0

G0 reported dense drift of at most 0.0001 TV and implied a gap of three or more
orders of magnitude. That compared 8 positions on a 1,300-token prompt. Over 16
positions on a 1,800-token prompt the dense model's worst-position TV is
0.0025–0.023. **The G1 magnitudes supersede G0's.** Worst-position TV grows with
the number of positions examined, so magnitude claims need a fixed position
budget and many prompts — which the main study provides.

## What this does not show

- **Population estimates.** The 11 boundaries per run share one prompt; they are
  not independent samples. The magnitudes describe one prompt per model.
- **Tool-call changes.** The prompt is raw text without a chat template.
- **The sliding-window model.** Spark was not run in G1; its k=1024 anomaly from
  G0 is still open.
- **A quantization effect.** G0's IQ4_XS hybrid flipped at position 1; G1's
  Q4_K_M hybrid flipped at positions 4–5 in 5 of 23 cases. Prompt and
  quantization both changed, so the two cannot be separated.

## Consequence

The exactness condition is precise enough to state as an engineering rule and
to propose as a documentation fix for llama.cpp's `cache_prompt` note, whose
current wording says only that results "can" be nondeterministic. The
main-study mitigation arm (snapping reuse boundaries down to `n_ubatch`
multiples) now rests on a confirmed mechanism rather than an inference.
